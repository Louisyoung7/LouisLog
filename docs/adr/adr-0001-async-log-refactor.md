# ADR-0001: LouisLog 重构为异步日志：前端入队，后台批量落盘

## 状态
Accepted（已实现，3 个单测全绿，翻滚 100/100 条零丢失，压测验证）
参与者：louis + AI 助手

## 背景
原同步日志在调用线程内联完成格式化与 I/O，随并发规模增长暴露出一系列问题：

- CON-001: 同步日志的磁盘/终端 I/O 延迟直接转化为业务线程延迟，前端无法剥离
- CON-002: 全局互斥锁覆盖格式化与 I/O 全路径，多线程吞吐被串行化（压测 4/8 线程
  总吞吐 ≈ 单线程速率 ~300K msg/s，8 线程反而慢于 4 线程）
- CON-003: 文件流、配置、翻滚逻辑等共享状态在多线程下存在数据竞争风险
- CON-004: 进程退出时未落盘的日志不能丢失；FATAL 级别日志必须可靠落盘
- CON-005: 日志文件按大小翻滚，std::rename 在目标存在时静默覆盖，同毫秒多次翻滚会丢日志
- CON-006: std::localtime 非线程安全（glibc 静态缓冲区 + 内部全局锁），
  前端并发格式化构成数据竞争，同时形成隐藏的进程级串行点

## 决策
采用前端/后端异步模型（muduo AsyncLogging 风格）重构 LouisLog：

- DEC-001: 前端线程仅做锁外格式化并入队即返回；后台 worker 线程负责全部 I/O
- DEC-002: 队列机制采用 std::deque + std::mutex + condition_variable::wait_for
  （带谓词，3 秒超时兜底刷新）；写入完成由 writing_ 标志 + 第二个条件变量通知 flush
- DEC-003: I/O 全部移到锁外：worker 批量 move 出队列、持锁取配置快照
  （target/logFile），解锁后写文件与终端，前端可继续入队
- DEC-004: 资源所有权不变式——fileStream_ 由 worker 锁外独占写；
  其他线程仅在持锁且 !writing_ 或 join 之后访问；init 重启时先 join 再关旧流
- DEC-005: 配置读写——level_/target_/maxFileSize_/stopped_ 用 std::atomic 无锁读写；
  低频字符串配置（logFile_）走锁内快照
- DEC-006: FATAL 级别在前端同步 flush（等待队列清空且 writing_ 完成），保证关键日志不丢
- DEC-007: 时间戳使用 localtime_r + 栈上 std::tm——修复数据竞争的同时
  消除 glibc tzset 全局锁串行点，多线程吞吐提升 3~4.5 倍（8 线程达 1.9M msg/s）
- DEC-008: 翻滚文件名同毫秒去重：目标名已存在则追加序号（.1、.2…），
  防止 std::rename 静默覆盖（配合 .gitignore 排除测试日志产物）

## 备选方案

### ALT-001: 保持同步日志，仅优化锁粒度
- 否决原因：I/O 延迟本质上无法从前端剥离，CON-001 无解；实测多线程吞吐被锁串死，
  精细化锁无法改变"每条日志同步付出一次 I/O 代价"的结构性缺陷

### ALT-002: 双缓冲异步模型（buffer 满页/超时交换）
- 否决原因（本阶段暂缓）：需要 buffer 池与交换语义，实现复杂度显著高于单队列；
  当前单队列 + 批量落盘已达 1.9M msg/s，瓶颈收敛到自身队列锁，满足需求。
  保留为下一阶段优化方向

### ALT-003: 无锁 MPSC 队列
- 否决原因：实现与正确性验证成本高；mutex + cv 在当前规模实测足够，
  不为尚未出现的瓶颈引入无锁复杂度
