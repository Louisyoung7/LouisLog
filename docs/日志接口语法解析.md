# 源码
```cpp
// 包装器：在调用点捕获 source_location。
// 不能直接给变参函数加尾置默认实参（fmt, args..., loc = current()）：
// 变参包推导时会吞掉全部剩余实参，带默认值的尾参无法参与推导，编译报
// no matching function。cppreference 推荐用此模式绕过：
// loc 的求值发生在包装器构造函数的默认实参中，仍处于用户调用点。
template <typename... Args>
struct with_source_location {
    std::format_string<Args...> fmt;
    std::source_location loc;

    // 构造参数必须用 U&& 而非 std::format_string<Args...>：
    // 后者会造成 字面量->format_string->包装器 连续两次用户自定义转换，
    // 隐式转换序列非法；U&& 让字面量直接绑定参数，format_string 的构造在函数体内完成
    template <typename U>
        requires std::constructible_from<std::format_string<Args...>, U&&>
    consteval with_source_location(U&& u, std::source_location l = std::source_location::current())
        : fmt(std::forward<U>(u)), loc(l) {}
};

// 统一核心：级别过滤在格式化前，I/O 仍由 LouisLog 后台线程异步完成
template <typename... Args>
void emit(LogLevel level, with_source_location<std::type_identity_t<Args>...> f, Args&&... args) {
    auto& logger = LouisLog::getInstance();
    if (!logger.shouldLog(level)) return;  // 过滤在格式化前
    logger.log(
        level, f.loc.file_name(), static_cast<int>(f.loc.line()),
        std::format(f.fmt, std::forward<Args>(args)...)
    );  // 编译期检查格式串
}

template <typename... Args>
void info(with_source_location<std::type_identity_t<Args>...> f, Args&&... args) {
    detail::emit(LogLevel::INFO, std::move(f), std::forward<Args>(args)...);
}
```

# 完整解析

## 一、这段代码要解决的核心问题

### 1.1 用户想要的 API

理想情况下我们希望用户这样调用：

```cpp
LouisLog::info("x = {}", x);   // 想自动获得调用点 file/line
```

背后 `info` 需要拿到三样东西：`fmt` 格式串、`args...` 参数、`source_location`。

### 1.2 直接写在变参模板里是不行的

```cpp
// ❌ 编译失败
template <typename... Args>
void info(std::format_string<Args...> fmt, Args&&... args,
          std::source_location loc = std::source_location::current());
```

原因：`Args&&... args` 是一个**参数包**。C++ 规则规定，函数模板中参数包**之后**不允许再出现需要从实参推导的参数（带默认值也一样）。参数包会贪婪地把所有剩余实参都吞掉，编译器无法判断“哪个实参属于 `loc`”。结果就是 `no matching function`。

> 简单说：**变参包必须是最后一个参数**，无法在其后追加带默认值的尾参。

### 1.3 解决思路：把 `fmt` 和 `loc` 打包成一个对象

既然不能在 `info` 上挂尾置默认参数，那就把这个默认参数“下沉”到一个**包装类型的构造函数**里：

```
用户写 "x = {}" 
   → 隐式转换构造 with_source_location{fmt="x = {}", loc=current()}
   → 传给 info(f, args...)
```

在这个构造函数里，`loc` 是普通函数参数的默认实参，**不再受变参包规则约束**，同时 `current()` 的求值点仍然发生在用户书写 `info(...)` 的那一行——`source_location` 的“调用点捕获”语义得以保留。

## 二、逐块拆解

### 2.1 `with_source_location`

```cpp
template <typename... Args>
struct with_source_location {
    std::format_string<Args...> fmt;
    std::source_location loc;

    template <typename U>
        requires std::constructible_from<std::format_string<Args...>, U&&>
    consteval with_source_location(U&& u,
        std::source_location l = std::source_location::current())
        : fmt(std::forward<U>(u)), loc(l) {}
};
```

**① 为什么构造函数用 `U&&` 而不是直接写 `std::format_string<Args...>`？**

如果写成：

```cpp
consteval with_source_location(std::format_string<Args...> f, ...);
```

那么用户传字符串字面量 `"x = {}"` 时，编译器要做的隐式转换链是：

```
const char[7]  →  std::format_string<Args...>  →  with_source_location<Args...>
                 (用户自定义转换)                  (用户自定义转换)
```

**一次隐式转换序列中最多只能有一次用户自定义转换**，两次就非法了。

改成 `U&& u` 后：

```
const char[7]  →  U&& u  （完美引用绑定，无需转换）
       然后函数体内：fmt(std::forward<U>(u)) 
       → 在 fmt 成员初始化时做一次 format_string 构造（此时允许）
```

这样只有**一次**用户自定义转换，符合规则。

**② `requires std::constructible_from<...>` 约束**

不是所有类型都能构造 `format_string`，例如 `int` 就不行。约束让非法的隐式转换在重载决议阶段被排除，而不是进入函数体才报错——这样错误信息更清晰，也避免了其他重载被错误匹配。

**③ 为什么是 `consteval`？**

`std::format_string` 的构造函数本身是 `consteval`，必须在编译期完成格式串合法性检查。因此包装器的构造函数也必须是 `consteval`——这意味着所有格式串检查在编译期完成，运行时零开销，且格式串非法时直接编译报错。

**④ `std::source_location::current()` 作为默认实参**

这是整个技巧的灵魂：**默认实参的求值点位于调用点**。

用户写：
```cpp
info("x = {}", x);   // 这一行
```

编译器会：
1. 发现第一个形参是 `with_source_location<...>`，需要从 `"x = {}"` 隐式转换；
2. 构造这个对象时调用 `with_source_location(U&&, source_location = current())`；
3. `current()` 作为默认实参，其求值点被定义为**第 1 步里那个调用表达式的位置**，也就是用户写 `info("x = {}", x)` 的那一行。

于是 `loc` 精确捕获到用户的调用点。

### 2.2 `emit`：统一的核心

```cpp
template <typename... Args>
void emit(LogLevel level,
          with_source_location<std::type_identity_t<Args>...> f,
          Args&&... args) {
    auto& logger = LouisLog::getInstance();
    if (!logger.shouldLog(level)) return;   // 过滤先于格式化
    logger.log(
        level, f.loc.file_name(), static_cast<int>(f.loc.line()),
        std::format(f.fmt, std::forward<Args>(args)...)
    );
}
```

**① `std::type_identity_t<Args>...` 的作用**

`type_identity_t<T>` 就是一个 `T` 的别名（`using type_identity_t = T;`）。但它出现的**上下文**不同：

- 模板参数推导时，出现在 `type_identity_t<...>` 里的模板参数被视为**非推导上下文**（non-deduced context）。
- 因此 `f` 这个形参的类型不会参与 `Args...` 的推导；`Args...` 完全由第二个形参 `Args&&...` 从实参推导出来。
- 推导出 `Args...` 之后，`f` 的类型被“反向确定”为 `with_source_location<Args...>`。

如果没有 `type_identity_t`，`with_source_location<Args...>` 本身也会参与推导，可能造成歧义或推导失败。这是 C++ 常见的“定向推导”技巧。

**② `shouldLog` 在 `std::format` 之前**

如果当前级别被过滤掉，连格式化都不做——这就是性能优化点。格式化（尤其涉及浮点、复杂类型）可能很昂贵。

**③ `std::format(f.fmt, ...)` 编译期检查**

`f.fmt` 的类型是 `std::format_string<Args...>`，这个类型保证了构造时已经在编译期校验过格式串与参数类型的匹配。运行时不会因为格式串错误抛异常。

### 2.3 `info`：门面

```cpp
template <typename... Args>
void info(with_source_location<std::type_identity_t<Args>...> f, Args&&... args) {
    detail::emit(LogLevel::INFO, std::move(f), std::forward<Args>(args)...);
}
```

只是把日志级别固定成 `INFO`，其余逻辑委托给 `emit`。

- `std::move(f)`：`f` 是按值传进来的局部对象，移动给 `emit` 避免拷贝。
- `std::forward<Args>(args)...`：保持实参的值类别（左值仍左值，右值仍右值）。

## 三、用户视角：一次调用的完整历程

用户写：

```cpp
int x = 42;
LouisLog::info("x = {}", x);
```

### 步骤 1：重载决议，推导 `info` 的 `Args...`

签名：
```cpp
info(with_source_location<std::type_identity_t<Args>...> f, Args&&... args)
```

- 第一个形参：`type_identity_t` 让 `Args...` 成为非推导上下文，跳过。
- 第二个形参：`x` 是 `int` 左值 → `Args&&` 被推导为 `int&` → `Args = int&`。
  - 若用户传右值 `42`，则 `Args = int`。
- 于是 `f` 的类型确定为 `with_source_location<int&>`（或 `int`）。

> 实际中参考实现里 `format_string` 会处理引用类型，所以 `int&` 没问题。

### 步骤 2：把 `"x = {}"` 隐式转换成 `with_source_location<int&>`

- 候选构造函数模板：
  ```cpp
  template <typename U>
      requires std::constructible_from<std::format_string<int&>, U&&>
  consteval with_source_location(U&& u, source_location l = current());
  ```
- 从 `"x = {}"`（类型 `const char(&)[7]`）推导 `U = const char(&)[7]`。
- 检查约束：`constructible_from<format_string<int&>, const char(&)[7]>` ✓（`format_string` 有从字符数组构造的 consteval 构造函数）。
- 默认实参 `current()` 求值点 = `info("x = {}", x)` 这一行。
- 函数体（编译期）：
  - `fmt("x = {}")` → 编译期校验 `"x = {}"` 与 `{int&}` 匹配 ✓ → 存入 `fmt` 成员。
  - `loc` 存入文件、行号、列号。
- 因为构造函数是 `consteval`，整个对象在编译期构造完成。

### 步骤 3：进入 `info` 函数体

- `f` 是刚才那个编译期构造好的 `with_source_location<int&>`。
- 调用 `detail::emit(LogLevel::INFO, std::move(f), std::forward<int&>(x))`。

### 步骤 4：`emit` 再次推导 `Args...`

- `emit` 的第二个形参 `Args&&...` 接收 `int&` → `Args = int&`。
- 第一个形参 `f` 是 `with_source_location<int&>`，与 `type_identity_t<int&>...` 一致。
- 匹配成功。

### 步骤 5：`emit` 内部执行

```cpp
auto& logger = LouisLog::getInstance();
if (!logger.shouldLog(LogLevel::INFO)) return;

logger.log(
    LogLevel::INFO,
    f.loc.file_name(),                    // 编译期捕获的调用点文件名
    static_cast<int>(f.loc.line()),       // 行号
    std::format(f.fmt, std::forward<int&>(x))  // 编译期已校验的格式化
);
```

`logger.log(...)` 把已经格式化好的字符串投递到后台线程异步输出，用户线程不做 I/O。

## 四、为什么这样写是“甜点级”设计

| 目标 | 实现机制 |
|---|---|
| 用户调用简洁 | `info("fmt {}", args...)` 无额外包装 |
| 自动捕获调用点 | 默认实参 `current()` + `consteval` 构造 |
| 绕开变参包尾置默认参限制 | 把默认参数放进包装器构造函数 |
| 编译期格式串校验 | `std::format_string<Args...>` 的 consteval 构造 |
| 只允许一次自定义转换 | 构造函数形参用 `U&&`，`format_string` 在体内构造 |
| 定向推导 `Args...` | `std::type_identity_t` 屏蔽 `f` 的推导参与 |
| 过滤先于格式化 | `shouldLog` 提前返回 |
| 运行时无 I/O 阻塞 | `logger.log` 异步投递 |

---

## 五、一个易错点总结

1. **不要**把 `with_source_location` 的构造函数写死成 `format_string<Args...>` 形参——会触发两次自定义转换。
2. **不要**在 `emit` 里去掉 `std::type_identity_t`——否则 `f` 也参与推导，会和 `args...` 的推导冲突/歧义。
3. **不要**把构造函数写成 `constexpr`——`format_string` 的构造是 `consteval`，必须匹配。
4. `std::move(f)` 和 `std::forward<Args>(args)...` 的分工：`f` 是局部值 → move；`args` 是转发引用 → forward。
5. `current()` 必须在**默认实参**位置——如果写到函数体里，捕获的就是 `with_source_location` 构造函数内部的调用点，而不是用户调用点。
